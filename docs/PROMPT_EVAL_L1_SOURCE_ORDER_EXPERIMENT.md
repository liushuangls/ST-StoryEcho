# L1 来源顺序优先候选实验

## 冻结方案（真实请求前）

上一轮 `l1-event-transition` 虽修复医疗例的顺序，却没有修复恋爱例，并新增了来源外的答复条件；继续在同一句叠加事件分类文字容易制造更长而重叠的规则。本轮改动另一处直接冲突的写作规则：生产 Prompt 一方面要求沿时间顺序，另一方面允许同一主题下合并互动。候选只收窄后者，把会改变含义的局部来源顺序设为优先约束。

方法继续参考 [OpenAI 官方模型提示指南](https://developers.openai.com/api/docs/guides/latest-model?model=gpt-5.5#prompting-best-practices)：只改一个与已证实错误直接相关的规则，以代表性用例和预先定义的停止条件判断，不根据运行中的答案继续补句。

### 唯一候选：`l1-source-order`

生产规则：

> 每个关键事件只写足以说明“触发或背景—发生的变化—结果或遗留问题”的内容。过程本身不影响人物选择和后续状态时，直接写结果；同一主题下连续发生的互动、尝试、训练、照料或争论合并，只保留新增结果、反转与意义。

候选替换为：

> 先按history_messages的messageId保持关键事件的局部先后，再压缩或归并主题。只有不改变“触发或要求—回应或决定—执行或结果”、人物选择、因果和行动阶段时，才可合并过程或直接写最终状态；否则按来源顺序保留这些节点。

这不是上一轮候选的追加或组合；生产中的事件阶段分类句保持原样。候选不含开发案例人物、答案、固定章节、结构化输出或字数目标，仅存在于 `evals/variants.ts`，`src/` 不引用。

生产整条规则为 104 个 Unicode 码点，候选为 119 个码点、303 UTF-8 字节；候选文本 SHA-256 为 `d936438e5ab79974a8a215b912078269aacb82c96d802bc2e74754312180e60c`。请求前 39 个相关离线测试和 TypeScript 检查通过，两份结果路径确认不存在。

### 开发集与硬门槛

先使用已完成 production 两轮基线的八个 L1 开发例。它们的来源、rubric、本地硬断言、生成模型、Judge、3,000 Token 上限和 temperature 均保持不变；四个既有 holdout 继续隔离。

必须同时满足：

1. 恋爱例两轮均保留“林晚提出边界 → 贺知远答应 → 删除动态”，且不得把“面试后考虑”写成答复取决于面试结果。
2. 医疗例两轮均保留“医生澄清 → 周宁纠误/作废 → 顾禾决定监测复诊”。
3. 偶像例两轮均不得把归档指示升级为已经归档。
4. 八例均无新的 major/critical 来源错误、关键硬断言失败、空响应或截断；主题组织变化不得明显遗漏独立剧情线。

两轮固定各执行八次生成和八次独立 Judge，不自动重试、不覆盖已有结果。Judge 总分只作辅助；逐来源可证伪错误优先。任何必过项失败即淘汰候选，不解封 holdout、不修改生产 Prompt，也不在同轮设计第二候选。

只有开发集通过，才对四个隔离 holdout 同时运行 production 与候选各两轮，并保持同样停止条件。留出结果不能用于修改当前候选；未通过则记录并停止，通过也只表示值得另行审查生产变更，不自动发版。

## 实测结果：未通过，不进入 holdout

两轮共完成 16 次生成和 16 次独立 Judge 请求，均无网络错误、空正文、截断或协议错误，全部 `finish_reason=stop`。两轮逐例 prompt hash、evaluation hash、评测协议、生成模型和 Judge 连接指纹一致。

| 指标 | Source-order R1 | Source-order R2 |
| --- | ---: | ---: |
| 完成生成 / Judge | 8 / 8 | 8 / 8 |
| 自动通过 | 5 / 8 | 8 / 8 |
| Judge 综合均分 | 94.8 | 98.7 |
| 压缩比最小 / 中位 / 最大 | 0.603 / 0.649 / 0.783 | 0.597 / 0.665 / 0.856 |
| 生成总 Token | 18,281 | 18,341 |
| Judge 总 Token | 50,579 | 48,704 |
| 请求耗时合计 | 451,866ms | 377,554ms |

结果文件与 SHA-256：

- `l1-source-order-dev-r1.json`：`59d79997154c6d669355d0bef15fd3350c37ee698f5f2833a7c4c8458dc0398b`
- `l1-source-order-dev-r2.json`：`ded2535a846cd586b6590b694d449d3e6de14411b178f7fc0f1eea8daf4c8fb3`

来源复核优先于自动总分，冻结的三个必过目标均未稳定满足：

1. **恋爱例失败 2/2。** 两轮都把删除未发布动态提前到林晚提出公开边界之前；R1 Judge 标为 major chronology，R2 标为 minor。两轮结尾还都把“周五面试在十八点前结束才成行”扩写成“奖学金面试结果决定是否成行”，而来源与世界背景均不支持面试结果影响关系或行程。R1 Judge 标为 major hallucination；R2 漏报该项，但逐来源检查仍直接可证伪。
2. **医疗顺序局部改善但未稳定合格。** 两轮均恢复“医学澄清 → 周宁纠误并作废 → 顾禾选择监测复诊”的先后；R2 明确由医生秦芮确认并得 100 分。R1 却写成“顾禾在门诊复查中确认”医学结论，改变了信息来源，关键因果项因此只得 partial，自动不通过。
3. **偶像完成阶段仍失败 1/2。** R1 再次把唐蔚“让运营归档评论区截图”写成“运营已归档”；R2 正确保留为指示。候选没有让该错误在两轮同时消失。

其余来源检查也显示波动：轨道站 R1/R2 都把氧气压力与无人机任务并列而没有明确连接，R1 因关键因果项不足而自动失败；世界书 R2 又把来源中的“博物馆修复师证件”具体化为“市立博物馆修复师证件”。本地硬断言和 forbidden claim 检查均通过，但不能覆盖这些语义归属与因果错误。

**决定：淘汰 `l1-source-order`。** 它没有修复最稳定的恋爱局部顺序，医疗有局部收益但伴随一次说话者/信息来源错绑，指示升级也仍复现。R2 的 8/8 不能覆盖 R1 的明确错误，更不能作为重复抽样直到通过的依据。四个 holdout 保持未运行；生产 Prompt、`src/`、bundle、版本和用户设置均不改。

这次结果还说明，`history_messages` 已经携带逐条 `messageId`，仅在 Prompt 中再次提高其优先级仍不足以让当前生成模型稳定保持局部事件图。下一步若继续，不宜再追加近义顺序规则；应把“输入表示是否能显式保留事件边”作为独立机制实验，例如在不改变原文的前提下给相邻关键动作提供可验证的顺序锚点，并先评估输入开销与错误绑定风险。本轮没有创建该机制、第二候选或任何生产改动。

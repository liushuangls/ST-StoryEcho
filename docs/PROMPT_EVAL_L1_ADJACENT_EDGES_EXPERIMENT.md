# L1 相邻消息顺序边实验

## 冻结方案（真实请求前）

两种纯 Prompt 候选都未稳定修复 L1 局部顺序：事件阶段候选和来源顺序优先候选仍会把“提出边界 → 答应 → 删除动态”改写为先删除后提出边界。现有输入虽然按 `messageId` 排列，但顺序只隐含在数组位置和单个编号中。本轮不继续叠加近义规则，改测一种最小输入表示：保留原始 `history_messages`，另附相邻消息的显式先后边。

实验方法参考 [OpenAI 官方模型提示指南](https://developers.openai.com/api/docs/guides/latest-model?model=gpt-5.5#prompting-best-practices)：只增加完成目标所需的最小上下文结构，固定成功标准和停止条件，再用代表性评测验证；官方指南不证明该表示一定有效。

### 候选：`l1-adjacent-order-edges`

原始消息数组完全不变。候选在其后添加：

```text
<history_order_edges>
[[前一messageId,后一messageId], ...]
</history_order_edges>
```

边覆盖每对相邻、有效的非系统消息，只声明时间先后，不声明因果、回应关系、主题归属或完成状态；不复制正文，不使用关键词、LLM 或 rubric 判断哪些事件重要。系统的 `history_messages` 证据说明只扩充为：

> history_order_edges若存在，每组[前一消息ID,后一消息ID]只重申相邻原文的先后，不添加因果、回应关系或完成状态；归并同一行动链时不得倒置这些边。

生产中的主题合并、事件阶段和其他规则保持原样。因此这是“输入字段 + 字段语义说明”的一个不可分 schema 候选，不与前两种 L1 候选叠加。它只存在于本地评测代码，`src/` 不读取或生成该字段。

### 风险与测量

- 价值假设：显式边降低模型在长 JSON 中重建局部顺序的负担，同时保留自由压缩无关过程的能力。
- 主要风险：模型把相邻先后误当因果、按消息逐条复述、输出膨胀，或仍忽略边；边本身也增加输入 Token。
- 每轮记录相对正式 production 基线的供应商报告 prompt Token 增量、请求字符增量、输出压缩比及正文长度。若平均 prompt Token 增加超过 10%，即使质量通过也不直接推广；若无稳定质量收益，任何开销都没有收益依据。
- 顺序边必须由输入消息机械生成，严格递增、只出现一次；原始消息 JSON、source evidence、rubric、硬断言和 evaluation hash 必须保持不变。格式异常须在请求前失败，不能静默省略边。

### 开发集与停止条件

沿用八个已有 production 两轮基线的 L1 开发例，生成模型、独立 Judge、3,000 Token 上限、temperature 和评测协议保持不变。候选固定运行两轮，每轮八次生成和八次 Judge，不自动重试或覆盖结果。

必过项：

1. 恋爱例两轮都恢复“提出边界 → 答应 → 删除动态”，不得新增面试结果决定恋爱答复或行程。
2. 医疗例两轮都保留由医生作出医学澄清，再由周宁纠误/作废、顾禾作出决定，不得错绑确认者。
3. 偶像例两轮都把截图归档保持为指示而非已完成。
4. 不得新增相邻即因果、关键独立线遗漏、major/critical 来源错误、硬断言失败、空响应或截断。

任一必过项失败即淘汰候选，不运行四个隔离 holdout、不设计同轮第二候选、不修改生产。只有开发集两轮及人工来源复核全部通过，才同时对 holdout 的 production 与候选各运行两轮；留出结果不能用于调整当前候选。

## 实测结果：有局部信号，但未稳定通过

两轮共完成 16 次生成和 16 次独立 Judge 请求，均无网络错误、空正文、截断或协议错误，全部 `finish_reason=stop`。两轮逐例 prompt hash、evaluation hash、评测协议、生成模型和 Judge 连接指纹一致。

| 指标 | Adjacent-edges R1 | Adjacent-edges R2 |
| --- | ---: | ---: |
| 完成生成 / Judge | 8 / 8 | 8 / 8 |
| 自动通过（历史硬断言） | 7 / 8 | 7 / 8 |
| Judge 综合均分 | 99.2 | 98.9 |
| 压缩比最小 / 中位 / 最大 | 0.562 / 0.684 / 0.777 | 0.601 / 0.677 / 0.792 |
| 生成输入 / 输出 Token | 17,030 / 2,257 | 17,030 / 2,228 |
| Judge 总 Token | 47,333 | 48,865 |
| 请求耗时合计 | 339,218ms | 385,991ms |

结果文件与 SHA-256：

- `l1-adjacent-order-edges-dev-r1.json`：`8d0faf4fc5791a5f569d1cb2b5f762e469101af6d39993e06a6dabefd6ee8ae9`
- `l1-adjacent-order-edges-dev-r2.json`：`d17df7c8d8d28689646e56542fb5bb040239a01519f7066abc5aca4e49e46a93`

相对对应 production 基线，每个十二消息用例固定增加 262 个请求字符和 126 个供应商报告输入 Token；两轮合计输入 Token 均增加 6.29%，低于预设 10% 警戒线。候选两轮输出合计 4,485 Token，production 为 4,505 Token，没有观察到输出膨胀。边数为有效消息数减一，因此构造时间、字段体积和额外内存均按消息数 O(n) 增长；本轮没有测真实超长批次的绝对耗时。

### 自动硬断言的两次误报

医疗两轮正文分别明确写出“未授权周宁代签任何治疗同意书”，语义上完整满足患者授权边界，Judge 也都判定该项完整。旧 `proxy-boundary` 词表只有“不授权／不能代签／不得代签”，漏掉“未授权”，所以两轮机械标红并非候选遗漏。历史结果及 evaluation hash 保持不变；实测结束后只为未来运行补入“未授权”，并增加离线回归。未来结果因此不能仅凭医疗 evaluation hash 与这两份旧文件自动等同比较。

### 来源人工复核

高分仍没有覆盖核心失败：

- **恋爱顺序只修好 1/2。** R1 仍先写贺知远删除动态并作出不公开承诺，后写林晚提出公开边界；明确的 `[1005,1006]` 相邻边没有阻止倒序，Judge 此轮漏报。R2 才正确保留“提出边界 → 答应 → 删除”，两轮均没有再把面试结果写成恋爱答复或行程条件。冻结门槛要求 2/2，因此不通过。
- **医疗主链实际正确 2/2。** 两轮都由医生秦芮先澄清，再由周宁纠误并作废、顾禾决定监测复诊，且都保留不得代签。R1 另把来源未指定提议者的“争论能否改成桌游”写成顾禾提议，属于 minor 归属扩写。
- **偶像场景没有把归档指示升级为完成。** R1 省略这项非 rubric 核心细节，R2 正确保留“让运营归档”；但 R2 又只写陆朔要求撤下错误预告，没有明确旧预告已经实际撤下，核心事实只得 mostly。
- **相邻即因果风险实际出现。** 世界书 R2 把“定位暗门后潮镜出现裂纹”写成“潮镜因此出现裂纹”，来源只给先后、未确认因果；这正是预先列出的表示风险。轨道站 R1 还从“照常发营养棒以防恐慌”补出“未公开氧气实情”，同样缺少来源支持。

**决定：淘汰 `l1-adjacent-order-edges`，不运行 holdout。** 它以 6.29% 输入开销换来一个有价值但不稳定的恋爱顺序改善，同时仍会忽略明确边，并出现一次把相邻先后强化为因果。当前证据不支持把这种冗余字段加入生产请求。

三轮结果共同说明：原始数组已经有顺序，重复编号或继续强调顺序不能稳定解决生成时的主题重组错误。下一步若继续，不应增加更复杂的全量边表；更合适的是先做**无生成调用的确定性输出校验研究**，判断能否从最终总结与原文中低成本发现“完成阶段升级”和关键边界遗漏。此前 L2 的 LLM 定位实验不稳定，因此新研究应先从可解释的本地规则和误报上限开始，不自动重写总结，也不接入生产。本轮没有创建该校验器。

离线验收：`npm run check` 通过（58 个测试文件、480 个用例），覆盖率门槛通过（语句/行 89.69%、分支 79.69%、函数 96.57%）；`git diff --check` 通过，`src/`、`dist/`、manifest 和 lockfile 与 HEAD 一致。两份结果确认由 Git 忽略。对 192 个版本控制/待提交文件及本轮结果做当前环境四个已配置 Key/连接地址的精确匹配，没有 API Key 命中；一个连接地址命中仍来自既有 provider 测试的公开端点夹具。此检查不穷尽未知秘密。本轮没有提交、推送、版本变更或浏览器设置改动。
